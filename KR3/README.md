# KR3. Интернет-магазин 🏪


## Архитектура системы

### Компоненты системы:

1. **API Gateway** - Маршрутизация запросов к соответствующим микросервисам
2. **Order Service** - Управление заказами и их статусами
3. **Payment Service** - Обработка платежей и управление счетами пользователей
4. **RabbitMQ** - Брокер сообщений для асинхронного взаимодействия
5. **SQL Server** - База данных для всех сервисов



## Функциональность

### Payment Service
- **Создание счета** - Один счет на пользователя
-  **Пополнение счета** - Увеличение баланса пользователя
-  **Просмотр баланса** - Получение информации о счете

### Order Service
-  **Создание заказа** - Асинхронный запуск процесса оплаты
-  **Просмотр списка заказов** - Получение всех заказов пользователя
-  **Просмотр статуса заказа** - Детальная информация о конкретном заказе

### API Gateway
- **Маршрутизация запросов** - Перенаправление к нужным сервисам
- **Обработка ошибок** - Централизованная обработка сбоев
- **Circuit Breaker** - Защита от каскадных сбоев


## Реализованные архитектурные паттерны

### 1. Transactional Outbox Pattern (Order Service)
- Обеспечивает атомарность между сохранением заказа и отправкой сообщения
- Гарантирует доставку сообщений о платежах

### 2. Transactional Inbox/Outbox Pattern (Payment Service)
- **Inbox**: Обеспечивает exactly-once обработку входящих платежных запросов
- **Outbox**: Гарантирует доставку ответов о результатах платежей

### 3. Exactly-Once Semantics
- Дедупликация сообщений по MessageId
- Предотвращение повторных списаний при ретраях
- Атомарные операции с балансом



## API Endpoints

### API Gateway

#### Orders
- `POST /api/orders` - Создание заказа
- `GET /api/orders/{orderId}` - Получение заказа по ID
- `GET /api/orders?userId={userId}` - Получение заказов пользователя

#### Accounts
- `POST /api/accounts` - Создание счета
- `GET /api/accounts/{userId}` - Получение информации о счете
- `POST /api/accounts/deposit` - Пополнение счета


## 🐳 Docker и развертывание

### Запуск системы
```bash
# Клонирование репозитория
git clone <repository-url>
cd KR3

# Запуск всей системы
docker-compose up -d

# Просмотр логов
docker-compose logs -f

# Остановка системы
docker-compose down
```

### Компоненты Docker Compose
- **kr3-apigateway**: API Gateway (порт 5000)
- **kr3-orderservice**: Order Service (порт 5001)
- **kr3-paymentservice**: Payment Service (порт 5002)
- **kr3-rabbitmq**: RabbitMQ (порт 5672, управление 15672)
- **kr3-sqlserver**: SQL Server (порт 1433)

По условию задачи у нас из сторонних источников есть user_id. Для тестирования достаточно просто сгенерировать любой guid и использовать его как аутентификатор пользователя. Это можно удобно сделать командой в консоли:
```
[guid]::NewGuid().ToString()
```

Также при тестировании важно уметь расшифровывать статус заказа, он представлен в виде enum, для удобства вынесу сюда:
```c#
public enum OrderStatus
    {
        Created, // 0 - создан
        PaymentPending, // 1 - ожиданиее произведения оплаты
        PaymentProcessed, // 2- процесс оплаты
        PaymentFailed, // 3 - недостаточно средств (оплата не удалась)
        Completed // 4 - Оплата успешно проведена
    }
}
```

В случае неуспешной оплаты, заказ так и останется висеть неоплаченным, то есть не будет такого, что как только у пользователя появятся деньги, у него тут же спишут деньги за неоплаченный заказ :)

### Swagger документация
Доступна по адресам:

- Payment Service: `http://localhost:5001/swagger`
- API Gateway: `http://localhost:5002/swagger`

P.s не смотря на то, что swagger доступен для всех микросервисов, понятно, что изначально предполагается, что пользователь работает с Api Gateway.
